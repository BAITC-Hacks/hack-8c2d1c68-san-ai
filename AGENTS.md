# Инструкции для агентов

## Цель и контекст

Команда хакатона: два разработчика и PM, отвечающий за бизнес-логику. На работу есть 5 часов, команда общается напрямую и вживую. Приоритет — работающий сквозной сценарий MVP, который команда может показать и объяснить.
Общайся по-русски; используй принятые в коде имена и стиль.
Перед работой прочитай `docs/PRODUCT.md`. `docs/WORKFLOW.md` нужен при разделении работы, интеграции и подготовке демо.
Актуальные указания пользователя уточняют эти документы. Не превращай предположения в подтверждённые требования.

## Выполнение

- Сначала осмотри существующие файлы, применимые инструкции и, если есть Git, status/diff. Сохраняй чужие изменения.
- Для нетривиальной задачи обозначь короткий план, затем реализуй и проверь результат. Рутинные обратимые решения принимай самостоятельно.
- Если неизвестность меняет бизнес-результат, контракт между разработчиками или объём MVP, задай конкретный вопрос. Пока ждёшь, выполняй независимую работу. Неблокирующие допущения обозначай явно.
- Делай минимальное законченное изменение по критериям приёмки. Не добавляй незапрошенные функции, инфраструктуру или масштабные рефакторинги.
- Используй уже выбранный стек и менеджер пакетов. Пока стек не определён, сначала выясни опыт команды; не создавай приложение на случайно выбранном стеке.
- Ищи актуальные API и настройки в официальной документации, если от них зависит реализация. Подключай инструменты и skills под конкретную задачу.

## Совместная работа

- Разработчики договариваются о разделении работы вживую. Не вводи трекер, карточки, ID, статусы или обязательные отчёты в файлах. При одновременной работе используй отдельные рабочие копии; worktree — при необходимости и уже настроенном Git.
- Уточняй у пользователя договорённости об API и общих файлах, если они нужны для текущего изменения и ещё не переданы в чат или код. Согласованные типы и примеры храни рядом с реализацией, когда это помогает интеграции.
- Не перезаписывай файлы, над которыми сейчас работает другой разработчик. При пересечении согласуй границы; изменения общих зависимостей и lock-файла объединяет один назначенный владелец.
- Не создавай дополнительных агентов автоматически. Для обычной задачи достаточно одной сессии; отдельный review можно запросить явно.
- О готовом результате и блокерах сообщай кратко в чате. Пользователь передаст нужное команде вживую. Не требуй документировать каждую договорённость.

## Проверка и завершение

- Команды запуска и проверки бери из фактических manifest/scripts и README; не выдумывай команды. После появления приложения запиши проверенные команды в README.
- Проверь затронутое поведение. Для бизнес-логики, API и исправления ошибок добавляй полезные проверки; для простых текстовых правок достаточно осмотра diff.
- Для UI проверь основной сценарий в браузере и состояния загрузки, пустого результата и ошибки, если они затронуты. Если браузер недоступен, укажи это.
- Для внешних AI/API-вызовов предусмотрите понятную ошибку и ограниченное ожидание. Тестовые данные и демонстрационные ответы обозначай явно; не выдавай заглушку за живую интеграцию.
- Не помещай секреты в код, клиентский bundle, Git или логи. В `.env.example` указывай только имена и безопасные примеры.
- В конце сообщи: что готово, как проверено, что не проверено/мешает, что нужно следующему разработчику. Не называй непроверенную работу проверенной.

## Текущее состояние

При создании инструкций 2026-09-23 папка была пустой, Git и приложение отсутствовали. Продукт, стек, точное время сдачи и роли разработчиков пока не определены; продолжительность работы — 5 часов. Это исходная справка: сверяй её с текущими файлами. Правила организаторов нельзя выводить из названий документов; статус источников указан в `docs/PRODUCT.md`.
