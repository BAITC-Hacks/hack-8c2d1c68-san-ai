# Document Intelligence — выполненная работа

Состояние на 23 сентября 2026 года. Зона Full-stack 1 из
[плана проекта](../SAN_AI_PROJECT_PLAN.md). Дедлайн, указанный пользователем:
23 сентября, 17:00.

## Что реализовано

- Локальное чтение DOCX через `parseDocx`: текст абзацев, включая абзацы таблиц,
  идентификаторы документа и фрагментов, сторона ДО/ПОСЛЕ, номера абзацев
  и явно записанных пунктов. Подробности: [DOCX_PARSING.md](DOCX_PARSING.md).
- CLI `npm run --silent documents:parse -- before|after "путь.docx"`:
  JSON в stdout, понятная ошибка в stderr и ненулевой код выхода при отказе.
- Проверка источников `verifySource`: цитата должна существовать в указанном
  документе, комплекте и фрагменте. Подробности: [DOCUMENT_SOURCES.md](DOCUMENT_SOURCES.md).
- Ограничения размера DOCX и XML, обработка повреждённых и пустых документов,
  предупреждения о неполноте чтения, правках и автоматической нумерации.
- Зависимости `fflate` и `fast-xml-parser`, обновлённый npm lockfile,
  инструкция запуска в [README](../README.md).

UI и существующий API графа не изменены. Документы обрабатываются локально,
внешние AI/API не вызываются. Исходные DOCX и результаты их обработки не
включаются в Git; локальные JSON находятся в `.data/document-parsing/`.

## Как проверено

- `npm test`: 20 тестов прошли — 7 проверки источников, 7 DOCX-парсера,
  6 существующей БД и API-контрактов.
- `npm run typecheck`, `npm run lint`, `npm run build`: прошли.

Это проверка извлечения текста, не точности определения функций или изменений.

AI-интеграция и сквозное сравнение документов не проверялись.

## Что осталось и что передать второму разработчику

1. Согласовать canonical JSON подразделений, функций, связей, ограничений
   и источников. Существующий `SourceFragment` — внутренний формат фрагментов,

   ответа, цитат, понятными ошибками и ограниченным ожиданием.
3. Реализовать серверную загрузку и UI комплектов ДО/ПОСЛЕ.
4. Добавить PDF и XLSX согласно плану MVP.
5. Передать извлечённую модель второму разработчику для matching, findings,
   evidence и заключения; проверить сквозной сценарий на реальных документах.

Парсер можно использовать через `parseDocx(bytes, filename, side)` из
`src/lib/server/docx-parser.ts`. Его `fragments` совместимы с `verifySource`.
Совпадение цитаты подтверждает происхождение текста, но не правильность
его интерпретации. Неполный комплект не доказывает потерю функции.

Корпоративные интеграции (включая 1С и enbek.kz) отложены на развитие.
Развёртывание локальной LLM пока не реализовано и не выбрано как обязательное.

## Подключение OpenAI

Добавлен серверный адаптер `src/lib/server/openai-json.ts` для Responses API
со строгим JSON Schema, `store: false`, таймаутом 90 секунд и отменой запроса.
Ключ читается из `OPENAI_API_KEY`; модель — из `OPENAI_MODEL`, по умолчанию
`gpt-4.1-mini`. Ключи и сырые тела ошибок провайдера не логируются.

Команда `npm run ai:check` читает `.env.local` и выполняет один небольшой
платный API-вызов на синтетическом тексте. Живая проверка выполнена успешно;
пользовательские документы в ней не отправлялись. 33 теста проекта,
ESLint и TypeScript прошли. Четыре новых теста проверяют формат запроса,
ошибки провайдера, незавершённые/некорректные ответы и таймаут на локальных заглушках.

Это подключение транспорта, не готовое извлечение организации и не сравнение.
Structured extraction документов и кнопка сравнения пока не подключены.
Перед интеграцией нужен согласованный canonical JSON / endpoint второго разработчика;
вопрос передан пользователю. Произвольный JSON от адаптера имеет тип `unknown`:
его должен валидировать конкретный модуль извлечения перед использованием.

Основание реализации: [официальная документация Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
