# Сравнение ДО / ПОСЛЕ

Модуль Organization Audit по PRODUCT_SPEC 0.1 и DATA_CONTRACT. Исходные
извлечения, CURRENT и предложенная организация не изменяются. Рекомендации
остаются `proposed`; решения accept/reject/approve в этот этап не входят.

## Пользовательский сценарий

1. На `/` добавить документы ДО/ПОСЛЕ и нажать «Построить структуры».
2. Проверить схемы рядом, переключить «Схема / Список», раскрыть «Показать источник».
   Функции доступны в дополнительном разделе. Legacy extraction без entity_type
   обновляется при явном построении, используя существующий `refresh=1`.
3. Нажать «Сравнить ДО и ПОСЛЕ». Факты и цитаты передаются через прежний API.
4. На экране «Результаты анализа» изучить «Изменения» и «Рекомендации».
   «Почему система так решила» показывает точные цитаты ДО/ПОСЛЕ и объяснение.
5. Детали сравнения и подразделения доступны отдельно. Модель, предупреждения
   и JSON вынесены в «Техническая информация». Неполный результат явно отмечается,
   неизвестные метрики не заменяются нулями; доступно «Повторить анализ».
6. Вернуться к структурам и документам. Изменение комплекта требует обновления
   структур и нового сравнения. Обычный возврат не сбрасывает результат.

Актуальное UX-ТЗ: [UX_REDESIGN_SPEC.md](UX_REDESIGN_SPEC.md).
Проверки frontend: [UX_REDESIGN_HANDOFF.md](UX_REDESIGN_HANDOFF.md).

## Логика

- Сервер проверяет сторону, обработку всех фрагментов и отсутствие повторных
  копий на одной стороне. Одинаковый исходный файл ДО и ПОСЛЕ допустим.
  Цитаты и координаты повторно сверяются с parser-owned `parsed.json`.
- Canonical-проекция сохраняет `before/current` и `after/proposed` отдельно.
- AI сопоставляет владельцев, переименования и подтверждённые сокращения.
  Нормализация имени меняет только регистр, кавычки, пробелы и ё/е.
  Группы соответствия относятся к анализу и не переписывают исходные ID.
  Разные владельцы, родитель и подчинённый, подразделение и должность не сливаются.
- Функции ДО обрабатываются пакетами по 24. Каждый пакет видит **все** функции
  ПОСЛЕ: действие, объект, область, условия, modality, responsibility_type и цитаты.
  Несколько соответствий допустимы. Частичные/неуверенные — `needs_review`.
- Все функции ПОСЛЕ отдельно проверяются на пары дублирования/конфликта.
  Дублирование требует разных подтверждённых владельцев обязанностей одного типа;
  вертикаль управления исключается. Конфликт ограничен одной подтверждённой
  вертикалью: запрет против назначения действия либо исполнение против
  потенциально несовместимой другой ответственности. Конкретную несовместимость
  и пересечение областей модель объясняет по цитатам. Обычное консультирование
  само по себе не конфликт. Между независимыми вертикалями конфликты этим MVP
  не устанавливаются; это не нормативный rule engine.
- Сервер проверяет ID, стороны, типы, confidence, полное покрытие владельцев и
  функций ДО. Некорректный/неполный ответ приводит к ошибке всего запуска.
- Порог confidence 0.8 — настройка MVP, не калиброванная вероятность. Для
  `not_found` это уверенность в отсутствии соответствия в обработанном комплекте.
- `lost` формируется только для обязанности с уверенным `not_found`, известным
  владельцем и без известных пробелов. Права/запреты без соответствия — на проверку.
- Рекомендации используют три прозрачных шаблона по findings: закрепить владельца,
  уточнить границы, разделить несовместимые обязанности. `target_changes: []`.
  Заключение собирается из счётчиков анализа без дополнительной генерации фактов.

## Полнота и ограничения

Отклонённые записи, неизвестные сущности/владельцы и предупреждения о пропусках
запрещают выводы о возможной потере и создании подразделений. UI показывает
«Недостаточно данных», а не нулевой риск потери. Обычные предупреждения о границах
парсера (основной текст DOCX, текстовый PDF, значения XLSX, нумерация Word)
сохраняются и ограничивают вывод, но сами по себе не запрещают потенциальный lost
в прочитанном тексте. Полнота исходного комплекта никогда не считается доказанной.
Нулевое число findings не означает отсутствие рисков. Отброшенные гипотезы рисков
подсчитываются в предупреждении.

Создание подразделения показывается как потенциальное. Слияния/разделения разных
подразделений не моделируются одной группой владельца; неоднозначность остаётся
на проверку. Полнота иерархии зависит от Document Intelligence.

## API и хранение

`POST /api/comparisons` принимает `{ before_ids: string[], after_ids: string[] }`
с UUID загруженных документов. Ответ: `{ result: ComparisonResult, cached }`.

`GET /api/comparisons?before=<uuid>&after=<uuid>` читает результат без AI.
Параметры before/after повторяются для нескольких документов. `&download=1`
добавляет скачивание. 404 — нет результата для текущих извлечений.

`POST /api/documents/:id/extract?refresh=1` явно повторяет извлечение и атомарно
заменяет успешный кэш; при ошибке прежний результат остаётся.

- До 10 документов, 250 функций, 100 классифицированных владельцев на сторону.
- До 500 000 символов JSON на AI-запрос; превышение — 422, без обрезки.
- До двух AI-запросов на запуск одновременно; весь запуск — до 10 минут.
- До двух запусков на процесс; повтор комплекта — 409, общая загрузка — 429.
  Блокировки локальные, не распределённые.
- Ключ учитывает версию алгоритма, модель и полное содержимое извлечений.
- Файлы: `DOCUMENT_STORAGE_DIR/.comparisons/<hash>.json` на постоянном диске.
- Перед публикацией повторно проверяется, что извлечения не изменились.
- Отмена, ошибка AI или неправильные ссылки не сохраняют частичный результат.
- Ошибки: 400 — выбор; 403 — чужой Origin; 413 — тело больше 4 КиБ;
  422 — неподготовленные данные; 502/503 — AI/сервер; 504 — отмена/таймаут.

## Проверки

`npm test` проверяет пять типов, неверные ссылки, неполноту, запреты, вертикаль
управления, отмену, кэш, изменение извлечения во время анализа и HTTP-вход.
Provider в unit-тестах — явно синтетическая заглушка; в приложении — OpenAI.

`npm run ai:check-comparison` выполняет реальные платные вызовы OpenAI на малом
синтетическом наборе: пять типов, переименование, смысловая переформулировка,
разные области обучения без ложного дублирования, кэш. Исходные DOCX и проверенные
извлечения создаются во временной папке; пользовательские файлы не читаются.
Это проверка сравнения, а не AI-извлечения: входная разметка здесь задана вручную.

На 23.09.2026: локальные тесты, lint, TypeScript, production build и живой
синтетический прогон прошли. Реальные редакции 8/9 и комплект организатора этим
прогоном не проверены. Реализация не означает развёртывание на сервере.

## Исправление скорости и ссылок — 23.09.2026

Актуальная версия алгоритма — comparison-v1.1-fast. Одинаковые наборы исходных
файлов определяются по parser-owned SHA-256 без AI: identical_sources=true,
analysis_complete=false, поскольку отдельный аудит внутренних рисков не запущен.
Разница стохастических извлечений не становится потерей или передачей функции.

Для разных комплектов: короткие ID с enum-ограничениями в JSON Schema; единая
таблица цитат без их повторения у каждой функции; пакеты сопоставления по 48,
рисков по 96; до четырёх независимых запросов одновременно. Для 93/76 функций
это 4 запроса вместо 9. Полный список ПОСЛЕ доступен каждому пакету.

Уточнение прежнего описания отказов: отдельная неверная/пропущенная ссылка теперь
не обрушивает весь анализ. Проверенные строки сохраняются, остальные явно
отмечены для проверки; analysis_complete=false и выводы о потере запрещены.
UI позволяет повторить неполный анализ через POST /api/comparisons?refresh=1
без повторного извлечения. Отказ провайдера или неверная структура всего ответа
по-прежнему являются ошибкой, а не успешным анализом.

На текущем локальном комплекте одинаковых файлов POST вернул 200 за 32 мс без AI.
Это отдельный замер, не SLA для разных документов. Live synthetic прогон после
оптимизации выявил все пять типов и исключил дублирование разных областей обучения.
Реальные разные редакции данным прогоном не проверялись.
