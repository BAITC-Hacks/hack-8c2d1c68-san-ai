# UX_REDESIGN_SPEC

**Version:** 0.1  
**Status:** Ready for implementation  
**Updated:** 2026-09-23  
**Owner:** Product / Captain  
**Scope:** frontend UX/UI, information architecture, navigation, presentation layer  
**Priority:** P0 for demo

---

## 1. Цель

Переработать текущий интерфейс SAN.AI так, чтобы новый пользователь без объяснений разработчика понимал:

1. что система сравнивает организационные документы ДО и ПОСЛЕ изменений;
2. какие документы нужно загрузить;
3. что произойдёт после загрузки;
4. на каком этапе анализа он находится;
5. что изменилось между версиями;
6. какие рекомендации предлагает система;
7. как вернуться назад, заменить или добавить документы и повторить анализ.

Основной пользовательский сценарий:

**Документы -> Структуры -> Результаты**

Внутренние технические этапы системы — parsing, extraction, chunks, canonicalization, AI requests, cache — не должны формировать основной интерфейс.

Главный принцип: **интерфейс должен отражать бизнес-задачу пользователя, а не внутреннюю архитектуру приложения.**

---

## 2. Что уже реализовано и должно быть переиспользовано

Редизайн не должен переписывать существующий backend без необходимости.

В текущем проекте уже есть:

- загрузка DOCX, PDF и XLSX;
- хранение документов;
- AI extraction;
- source evidence;
- canonical organization;
- визуализация структуры документа;
- режимы «Схема / Список»;
- comparison engine;
- сопоставление ДО / ПОСЛЕ;
- findings;
- типы Preserved / Transferred / Lost / Duplicated / Conflict;
- recommendations;
- partial analysis;
- повторный запуск анализа;
- progress states.

Нужно переиспользовать существующие API и контракты и переделать прежде всего:

- information architecture;
- порядок экранов;
- hierarchy информации;
- terminology;
- navigation;
- visual system;
- presentation of results.

---

## 3. Новый основной flow

Пользователь должен пройти три этапа.

### Этап 1. Документы

Пользователь загружает документы ДО и ПОСЛЕ.

### Этап 2. Структуры

Система показывает, как она поняла обе версии организации. Пользователь визуально проверяет структуру.

### Этап 3. Результаты

Система показывает:

- изменения;
- риски;
- evidence;
- рекомендации.

Рекомендации не являются отдельным обязательным шагом навигации. Они находятся внутри результатов.

---

## 4. Stepper

Под header постоянно показывать компактный progress stepper:

**1 Документы -> 2 Структуры -> 3 Результаты**

Состояния:

- current;
- completed;
- available;
- locked.

Правила:

- текущий этап выделен визуально;
- завершённый этап отмечен как completed;
- пользователь может вернуться на завершённый этап;
- нельзя перейти вперёд, если предыдущий этап не завершён;
- возврат назад не удаляет данные;
- изменение документов инвалидирует зависимые результаты.

---

## 5. Первый экран приложения

При первом входе пользователь должен попадать на этап **«Документы»**.

Не показывать extraction/results как главный первый экран.

Верхняя часть:

### SAN.AI

**Анализ организационных изменений**

Подзаголовок:

> Загрузите документы до и после реорганизации. SAN.AI восстановит структуру, найдёт изменения функций и подготовит рекомендации.

Вторичная подпись:

**Кейс АО «Казахтелеком»**

Подпись вторична и не должна конкурировать с названием продукта.

---

## 6. Визуальная система

Интерфейс должен визуально ассоциироваться с корпоративным кейсом Казахтелекома, но оставаться современным enterprise AI-продуктом.

### Требования

- основной фон: белый;
- дополнительный фон: очень светлый холодный голубой / серо-голубой;
- primary accent: синий / голубой;
- основной текст: тёмно-синий / почти чёрный;
- secondary text: нейтральный серо-синий;
- границы: светло-серые / голубовато-серые;
- success: зелёный только для успешного статуса;
- warning: amber;
- critical: красный.

Текущую зелёную визуальную тему убрать.

Если в репозитории или материалах команды есть официальный логотип / брендовый asset, использовать его. Не рисовать логотип Казахтелекома самостоятельно.

Не использовать случайные HEX по компонентам. Вынести design tokens, например:

~~~css
--brand-primary
--brand-primary-hover
--brand-primary-soft
--brand-primary-border
--text-primary
--text-secondary
--surface
--surface-secondary
--border
--success
--warning
--danger
~~~

### Общий характер интерфейса

- чистый;
- деловой;
- спокойный;
- минимум декоративных элементов;
- без тяжёлых теней;
- визуальная иерархия через whitespace, размер текста и границы;
- одна главная primary action на экран.

## 7. Этап 1 — Документы

### 7.1. Заголовок

**Сравнение организационных документов**

Текст:

> Добавьте действующие документы и новую редакцию. В каждом комплекте может быть несколько файлов.

### 7.2. Layout

Desktop: две равные колонки.

~~~text
┌─────────────────────────┐   ┌─────────────────────────┐
│ ДО изменений            │   │ ПОСЛЕ изменений         │
│                         │   │                         │
│ Upload area             │   │ Upload area             │
│                         │   │                         │
│ Uploaded files          │   │ Uploaded files          │
│                         │   │                         │
│ + Добавить ещё документ │   │ + Добавить ещё документ │
└─────────────────────────┘   └─────────────────────────┘
~~~

Mobile / narrow width: карточки располагаются вертикально.

### 7.3. Карточка «ДО изменений»

Описание:

> Действующие положения, оргструктура и документы, описывающие текущие функции.

Upload zone:

**Перетащите документы сюда**

Secondary text:

**или выберите их на компьютере**

CTA:

**Добавить документы**

Поддерживаемые форматы:

**DOCX, PDF, XLSX · до 10 МБ**

### 7.4. Карточка «ПОСЛЕ изменений»

Описание:

> Новая редакция или предлагаемая структура после реорганизации.

Поведение и визуальная структура симметричны карточке ДО.

---

## 8. Отображение загруженных документов

После загрузки файл должен сразу быть виден под соответствующей upload zone.

Пример:

~~~text
[DOCX] Положение_редакция_8.docx
       2,4 МБ
       Готов
                                  ⋮
~~~

Показывать:

- название;
- формат;
- размер;
- понятный статус;
- действие «убрать из анализа»;
- при необходимости открыть / скачать исходный файл.

Не показывать в основном интерфейсе:

- UUID;
- storage path;
- fragment count;
- chunk count;
- parser ID;
- technical extraction metadata.

Не использовать скрытый checkbox-list как основной способ выбора документов.

Главный экран показывает **текущий комплект анализа**, а не все файлы, когда-либо загруженные в хранилище.

---

## 9. Дозагрузка и изменение комплекта

Пользователь в любой момент на этапе 1 может нажать:

**+ Добавить ещё документ**

Новые файлы добавляются к уже выбранным.

У существующего файла должно быть действие:

**Убрать из анализа**

Удалять файл физически из storage для этого не обязательно. Достаточно исключить его из текущего комплекта.

---

## 10. Primary CTA этапа 1

Кнопка активна, если есть минимум один валидный документ ДО и один валидный документ ПОСЛЕ.

Главный CTA:

## **Построить структуры**

Под кнопкой:

> Определим подразделения, должности, функции и связи в обеих версиях.

Не использовать как основной CTA:

- «Подготовить к сравнению»;
- «Извлечь функции»;
- «Запустить extraction».

---

## 11. Processing state этапа 1

После нажатия «Построить структуры» показать один понятный progress state.

Заголовок:

**Анализируем документы**

Текст:

> Определяем структуру и функции обеих версий.

Допустимый статус:

~~~text
До изменений       Готово
После изменений    Анализируем…
~~~

Не показывать chunks и внутренние этапы AI.

Если обработка длительная:

> Анализ продолжается на сервере. Результат сохранится после завершения.

Для повторного клика primary button должен быть disabled.

---

## 12. Ошибки этапа 1

Ошибка должна сообщать:

1. что произошло;
2. что пользователь может сделать.

Пример:

**Не удалось обработать документ**

> Файл сохранён, но текст не удалось прочитать.

Actions:

- **Повторить**
- **Заменить файл**

Не показывать пользователю provider stack traces и внутренние ошибки.

---

## 13. Этап 2 — Структуры

После успешной обработки пользователь автоматически переходит на этап 2.

Заголовок:

## **Структуры ДО и ПОСЛЕ**

Подзаголовок:

> Проверьте, правильно ли SAN.AI восстановил организацию из документов.

### Layout

На desktop структуры показываются рядом:

~~~text
┌────────────────────────────┬────────────────────────────┐
│ Структура ДО               │ Структура ПОСЛЕ            │
│                            │                            │
│ [Схема] [Список]           │ [Схема] [Список]           │
│                            │                            │
│ organization structure     │ organization structure     │
└────────────────────────────┴────────────────────────────┘
~~~

На узкой ширине блоки становятся вертикальными.

---

## 14. Режим «Схема»

По умолчанию активен режим:

**Схема**

Показывать:

- подразделения;
- parent-child hierarchy;
- должности, если они распознаны.

Пример:

~~~text
Блок внутреннего аудита
├── ДНМ
└── ДККМ
~~~

и:

~~~text
Блок внутреннего аудита
├── ДИТААД
├── ДОА
├── ДНМ
└── ДККМ
~~~

Не показывать в каждой node:

**Функций и ограничений: 95**

Node должен быть визуально лёгким.

---

## 15. Режим «Список»

Переключатель:

**Схема | Список**

List view показывает:

- название;
- тип сущности;
- parent / принадлежность, если она известна.

При клике пользователь может открыть детали.

---

## 16. Evidence на этапе структуры

Evidence остаётся доступным, но вторичным.

Внутри основной схемы не показывать длинные цитаты постоянно.

Для node / entity использовать действие:

**Показать источник**

Источник открывается в side panel, drawer или компактном expandable detail.

Показывать:

- документ;
- пункт / абзац / страницу / лист;
- цитату.

---

## 17. Функции подразделений

Текущий большой default-блок «Функции и ответственность» с поиском, pagination и счётчиком «Найдено X из Y» убрать из основного flow.

Вместо этого использовать secondary action:

**Функции подразделений**

или secondary tab.

Пользователь открывает подробный список только при необходимости.

Не показывать по умолчанию:

- найдено X из Y;
- pagination технического extraction;
- model name;
- processed fragments;
- rejected items.

---

## 18. Actions этапа 2

В нижней action area:

Secondary:

**← Изменить документы**

Primary:

## **Сравнить ДО и ПОСЛЕ**

Использовать именно эту формулировку, так как сравниваются не только визуальные структуры, но и функции.

После нажатия:

**Сравниваем документы…**

Текст:

> Проверяем изменения подразделений и функций.

---

## 19. Возврат на этап 1

Если пользователь вернулся к документам и ничего не изменил:

- структуры остаются валидными;
- comparison result остаётся валидным.

Если пользователь:

- добавил документ;
- убрал документ;
- изменил текущий selection,

все зависимые результаты должны считаться устаревшими.

Показывать сообщение:

### Документы изменились

> Чтобы результаты учитывали новый комплект, заново постройте структуры.

Primary action:

**Обновить структуры**

Не использовать термин «outdated» в пользовательском тексте.

---

## 20. Этап 3 — Результаты

После успешного comparison пользователь попадает на один итоговый экран:

# **Результаты анализа**

Внутри две основные вкладки:

- **Изменения**
- **Рекомендации**

Отдельный обязательный navigation-step «Рекомендации» не нужен.

---

## 21. Вкладка «Изменения»

### 21.1. Summary

Вверху показать компактные summary metrics:

- новые подразделения;
- переданные функции;
- возможно потерянные функции;
- дублирование;
- потенциальные конфликты.

Пример:

~~~text
2
новых подразделения

4
переданные функции

1
возможная потеря

3
дублирования

1
потенциальный конфликт
~~~

Если показатель невозможно достоверно определить, не показывать ложный 0.

Использовать:

**Требует проверки**

или не показывать карточку.

### 21.2. Терминология

В UI:

- preserved -> **Сохранено**
- transferred -> **Передано**
- lost -> **Возможно потеряно**
- duplicated -> **Дублирование**
- conflict -> **Потенциальный конфликт**

Не использовать категоричные формулировки там, где вывод advisory.

---

## 22. Finding card

Каждый finding выводить отдельной карточкой.

Структура:

1. badge типа;
2. короткий заголовок;
3. короткое объяснение;
4. compact ДО / ПОСЛЕ;
5. действие для открытия evidence.

Пример:

### Передано

**Аудит информационных систем**

~~~text
ДО                         ПОСЛЕ
Директор направления   ->   ДИТААД
~~~

> Функция сохранена, но её владелец изменился.

Action:

**Почему система так решила**

---

## 23. Evidence finding

По нажатию «Почему система так решила» открыть детальный блок / drawer.

Показывать:

### ДО

- название документа;
- location;
- source quote.

### ПОСЛЕ

- название документа;
- location;
- source quote.

### Вывод системы

Короткое объяснение сопоставления.

Evidence и recommendation визуально не смешивать.

---

## 24. Risk и confidence

Risk можно показывать текстом:

- Низкий;
- Средний;
- Высокий.

Confidence percentage не делать prominent metric.

Не выводить крупно:

**Уверенность: 87%**

Если confidence нужен экспертному пользователю, перенести его в details или показать как вторичную характеристику сопоставления.

---

## 25. Детальное сравнение

Таблица всех функций полезна для эксперта, но не должна быть default content.

Внутри вкладки «Изменения» можно использовать secondary navigation:

- **Ключевые изменения**
- **Детали сравнения**
- **Подразделения**

Default:

**Ключевые изменения**

---

## 26. Partial analysis

Если comparison неполный, показать заметный warning:

### Анализ требует уточнения

> Некоторые источники не удалось надёжно сопоставить. Проверенные выводы сохранены, но потенциальные потери могут быть определены не полностью.

Actions:

- **Повторить анализ**
- **Продолжить с текущими результатами**, если это безопасно для существующей логики.

Нельзя подменять неизвестный результат нулём.

---

## 27. Вкладка «Рекомендации»

Рекомендации показываются на том же итоговом экране.

Карточка recommendation должна содержать:

### Проблема

Что обнаружено.

### Рекомендация

Что система предлагает сделать.

### Обоснование

Почему это предложено.

### Источники

Ссылка на evidence.

Визуально recommendation должна отличаться от finding.

Finding означает:

**SAN.AI обнаружил**

Recommendation означает:

**SAN.AI предлагает**

Recommendation использовать синюю suggestion styling, а finding — нейтральную / risk styling.

---

## 28. Что пока не входит в этот redesign scope

Следующие функции остаются в PRODUCT_SPEC как дальнейшее развитие, но не должны задерживать текущий UX redesign:

- accept / modify / reject recommendation;
- Proposed Target Organization;
- approval workflow;
- Workforce Alignment;
- HR integrations;
- scenario management.

Текущий redesign заканчивается качественным экраном:

**Результаты -> Изменения / Рекомендации**

---

## 29. Навигация назад

Явные actions:

На этапе 2:

**← Изменить документы**

На этапе 3:

**← Вернуться к структурам**

Не полагаться на browser Back как основной механизм.

Возврат не должен удалять текущее состояние.

---

## 30. Onboarding

Текущий автоматически открывающийся tutorial убрать.

Оставить secondary action:

**Как это работает?**

Tutorial открывается только по инициативе пользователя.

Допускается лёгкая first-use подсказка, но она не должна блокировать интерфейс.

Golden path обязан быть понятен без tutorial.

---

## 31. Информация, которую нужно убрать из основного UI

Скрыть из default flow:

- «Найдено 95 из 95»;
- processed fragments;
- rejected items;
- OpenAI model name;
- chunk counts;
- raw JSON download как prominent action;
- storage implementation messages;
- parser statuses;
- internal cache messages;
- UUID;
- длинные technical warnings.

При необходимости перенести в accordion:

**Техническая информация**

---

## 32. Privacy / AI notice

Не повторять техническое сообщение об OpenAI в нескольких местах.

Перед запуском анализа достаточно одной короткой notice:

> Для анализа содержимое выбранных документов обрабатывается AI-сервисом.

Не делать это главным визуальным элементом.

---

## 33. Button hierarchy

На каждом этапе должна быть одна главная primary action.

### Этап 1

**Построить структуры**

### Этап 2

**Сравнить ДО и ПОСЛЕ**

### Этап 3

Primary action не обязателен: пользователь изучает результат.

Все дополнительные actions — secondary / tertiary.

Использовать последовательно:

- Добавить документы
- Построить структуры
- Структура ДО
- Структура ПОСЛЕ
- Сравнить ДО и ПОСЛЕ
- Результаты анализа
- Изменения
- Рекомендации
- Показать источник
- Почему система так решила

Не смешивать для одного действия термины:

- подготовить;
- извлечь;
- обработать;
- запустить;
- проанализировать.

---

## 35. Empty states

Каждый empty state должен объяснять следующее действие.

Плохо:

**Здесь пока ничего нет**

Хорошо:

> Добавьте действующие документы организации.

CTA:

**Добавить документы**

---

## 36. Accessibility

Минимальные требования:

- keyboard navigation;
- visible focus;
- понятные button labels;
- color не является единственным индикатором;
- error / warning имеют icon + text;
- достаточный контраст текста;
- progress сообщает состояние через aria-live;
- critical action не должен быть доступен только через click на всю карточку.

---

## 37. Responsive behavior

Основной demo target: desktop 1280 px и выше.

При ширине ниже примерно 900 px:

- ДО / ПОСЛЕ становятся вертикальными;
- структуры становятся вертикальными;
- action areas не перекрывают контент;
- текст и buttons не должны обрезаться.

Mobile не является главным demo-case, но интерфейс не должен ломаться.

---

## 38. Не делать в рамках этой задачи

Запрещено без отдельной причины:

- переписывать Document Intelligence;
- менять DATA_CONTRACT;
- удалять evidence;
- заменять source citations генеративным пересказом;
- добавлять Workforce Alignment;
- добавлять HR integrations;
- возвращать employee graph как главный экран;
- делать сложные анимации;
- тратить время на decorative polish до завершения основного flow.

## 39. Definition of Done

Редизайн считается готовым, если человек, впервые открывший приложение, без tutorial и объяснений разработчика может:

1. понять, что система сравнивает документы ДО и ПОСЛЕ;
2. загрузить редакцию №8 в ДО;
3. загрузить редакцию №9 в ПОСЛЕ;
4. увидеть оба файла в текущем комплекте;
5. добавить дополнительный файл;
6. убрать файл из текущего анализа;
7. нажать **Построить структуры**;
8. понять, что идёт обработка;
9. увидеть Структуру ДО и Структуру ПОСЛЕ рядом;
10. переключить **Схема / Список**;
11. открыть source evidence при необходимости;
12. нажать **Сравнить ДО и ПОСЛЕ**;
13. увидеть ключевые изменения;
14. открыть finding и понять, почему система сделала вывод;
15. перейти во вкладку **Рекомендации**;
16. вернуться к структурам;
17. вернуться к документам;
18. изменить комплект;
19. получить понятное сообщение о необходимости обновить анализ;
20. повторно построить структуры и получить актуальный результат.

Если для прохождения этого сценария необходимо открывать «Как это работает?» или разработчику приходится объяснять последовательность действий, UX redesign не считается завершённым.

---

## 40. Ключевой критерий качества

Пользователь должен за первые 5 секунд получить ответы на три вопроса:

**Что это?**  
AI-анализ организационных изменений.

**Что нужно сделать?**  
Загрузить документы ДО и ПОСЛЕ.

**Что я получу?**  
Изменения, evidence и рекомендации.

Финальный golden path:

**Загрузил -> увидел, как система поняла документы -> сравнил -> получил ответ**
