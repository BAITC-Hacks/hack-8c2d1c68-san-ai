# Работа команды с Codex на хакатоне

У команды 5 часов, общение идёт напрямую и вживую. Карточки, статусы и трекер не используются. Рекомендации подготовлены 2026-09-23. Это предложенный рабочий процесс команды, а не правила организаторов.

## Выбор интерфейса

| Кто и задача | Рекомендация | Причина |
| --- | --- | --- |
| Разработчики: код, отладка, просмотр изменений | Codex extension в VS Code | Файлы, выделения и diff рядом с редактором |
| PM: требования, сценарии, анализ материалов, питч | ChatGPT App | Удобная работа с документами и другими инструментами |
| Разработчик, которому удобнее делегировать из приложения | Codex в desktop app | Подходит для работы с выбранной папкой; IDE можно оставить для отладки |

Это выбор удобства, а не утверждение о превосходстве модели в одном интерфейсе. Возможности зависят от установленной версии и доступа аккаунта. Официальные описания: [IDE extension](https://learn.chatgpt.com/docs/codex/ide), [ChatGPT desktop app](https://learn.chatgpt.com/docs/app).

## Быстрый старт

1. Откройте эту папку в VS Code и установите официальное расширение через ссылку Install the extension на странице IDE выше. Каждый разработчик входит в свой аккаунт.
2. Откройте новую сессию в корне проекта. Попросите: «Перечисли применимые инструкции из AGENTS.md и неизвестные параметры продукта». Это проверяет фактическую загрузку инструкций. После изменения инструкций используйте новую сессию.
3. Вживую договоритесь о главном сценарии, обязательных возможностях и времени сдачи. Передайте агенту нужный контекст в чате; PRODUCT можно кратко дополнить для следующих сессий. PM проверяет правила организаторов.
4. Выберите знакомый команде стек. Одному разработчику поручите начальный каркас, запуск и общую конфигурацию. После этого разделите UI и backend/AI либо независимые функции — по опыту команды.
5. Поместите инструкции в общий репозиторий вместе с кодом. Каждый работает в своей ветке и копии проекта. На одном компьютере для одновременных сессий используйте отдельные Git worktree после создания репозитория и первого коммита.
6. Перед разделением UI и API согласуйте пример запроса/ответа и ошибки. UI может работать на явно отмеченных тестовых данных по этому контракту.

`AGENTS.md` — автоматически обнаруживаемый файл инструкций Codex. Остальные Markdown-файлы читаются по ссылкам из него, а не являются специальными настройками. См. [механизм загрузки AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

## Ритм работы

- Первым соберите тонкий сквозной сценарий: ввод → обработка → результат. Рано проверьте запуск там, где будете показывать демо.
- Обсуждайте изменения и блокеры сразу вживую, без запланированных синков и ведения статусов.
- PM проверяет бизнес-результат и готовит примеры данных/питч; разработчики реализуют согласованные части приложения и смотрят изменения друг друга.
- Владелец интеграции объединяет небольшие готовые изменения и проверяет общий сценарий. Перед изменением контракта сообщите второму разработчику.
- Из пяти часов оставьте примерно последний час на исправления, повторяемое демо и сдачу. Интегрируйте код по ходу разработки.

## Готовые запросы

### Первая сессия разработчика

```text
Прочитай AGENTS.md и docs/PRODUCT.md. Помоги выбрать минимальный MVP
по нашей идее: [идея]. Сначала выясни только неизвестные, которые меняют
сценарий или стек. Затем предложи, как двум разработчикам разделить
работу без пересечения файлов. Код пока не создавай.
```

### Реализация изменения

```text
Реализуй [нужное поведение]. Мы договорились, что я делаю [моя часть],
а второй разработчик — [его часть]. Ожидаемый результат: [пример].
Проверь состояние файлов, внеси изменения и выполни доступные проверки.
Сохрани чужую работу. Кратко сообщи результат и ограничения в чате.
```

### Проверка перед объединением

```text
Проверь diff относительно [базовая ветка]. Ожидаемое поведение: [описание].
Ищи ошибки поведения, несовпадение API-контракта, проблемы с секретами
и поломку демо. Покажи конкретные находки с файлами и способом воспроизведения.
На этом проходе файлы не изменяй. Не придумывай замечания ради количества.
```

### Запрос PM

```text
По идее [идея] подготовь короткий brief для docs/PRODUCT.md:
пользователь, проблема, один главный сценарий, до трёх функций MVP,
что исключаем, примеры входа/результата и критерии приёмки.
Отдели подтверждённое от гипотез. Учти приложенные правила организаторов.
```

### Репетиция демо

```text
Пройди главный сценарий из docs/PRODUCT.md на текущем приложении.
Проверь нормальный ввод, некорректный ввод и отказ внешнего API.
Сообщи, где используются тестовые данные. Исправь блокирующие ошибки
в согласованном объёме и сообщи шаги демонстрации в чате.
```

## Что взять из опубликованных гайдов

1. **Короткий AGENTS.md и контекст по необходимости.** OpenAI рекомендует пересматривать разросшиеся инструкции и делать skills узкими по назначению. Здесь постоянные правила собраны в одном файле, детали вынесены в документы. [Гайд по skills и prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra).
2. **План → реализация → проверка → исправление.** Используйте этот цикл для доведения изменений до рабочего результата; итог достаточно сообщить в чате. [Run long horizon tasks with Codex](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex). Огромный автономный запуск из статьи — эксперимент, а не рекомендуемый режим сегодняшнего хакатона.
3. **Оркестрация агентов через SDK.** Есть готовый [пример Codex CLI + Agents SDK](https://developers.openai.com/cookbook/examples/codex/codex_mcp_agents_sdk/building_consistent_workflows_codex_cli_agents_sdk), но он помечен archived, а используемый Codex MCP server — deprecated. Сегодня не стоит тратить время команды на внедрение этого примера.

Моя рекомендация по настройке: начать с этих инструкций и устного разделения работы между разработчиками. Модель выбирать из доступных в своём интерфейсе; не фиксировать название в общих инструкциях. MCP и дополнительные skills добавлять при конкретной потребности. Для этого этапа отдельный plugin, глобальная конфигурация и собственный оркестратор не нужны.

## Готовность к показу

- В README есть фактически проверенные команды установки, запуска и проверки, а также имена нужных env-переменных.
- Главный сценарий воспроизводится с подготовленными данными.
- Загрузка и отказ внешнего сервиса не оставляют пользователя без объяснения.
- Тестовые данные/ответы обозначены; живая интеграция проверена отдельно, если входит в MVP.
- PM проверил результат, порядок демонстрации и требования к сдаче.
